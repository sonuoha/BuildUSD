# BuildUSD functional architecture

This directory contains a functional architecture of the current BuildUSD worktree. It models what the system does to information artifacts before showing which implementation elements perform each function.

## Deliverables

- `buildusd-functional-architecture.sysml` - normative SysML v2 textual model.
- `buildusd-functional-architecture-pilot.svg` - action view generated by the official SysML v2 pilot implementation.
- `buildusd-functional-architecture.svg` - presentation-ready functional architecture poster.
- `buildusd-functional-architecture.png` - raster preview of the poster.
- `render_functional_architecture.py` - reproducible SVG and vector-PDF renderer.
- `../../output/pdf/buildusd-functional-architecture-neat.pdf` - landscape vector PDF of the poster.

The `.sysml` file is the source of truth for model semantics. The presentation view adds repository-module allocations and uses an SSFD-like layout: compact verb-object function blocks, explicit triangular ports, left-to-right state flow, and separate dashed auxiliary-information buses. The three top-level chains are kept in aligned lanes so the full architecture remains readable on one sheet.

## Modelling basis

The architecture combines the two supplied papers as follows:

1. Start with the system boundary and the input/output states.
2. Characterize every state as an object with measurable attributes.
3. Trace the main information-artifact flow through successive verb-object functions.
4. Add auxiliary configuration, runtime, control, cache, and evidence flows.
5. Aggregate the function chains.
6. Allocate the functions to implementation elements only after the functional model exists.

This directly applies Yildirim and Campean's System State Flow Diagram method and the flow-tracing, common-vocabulary, causal ordering, aggregation, and topology principles described by Kurfman, Stone, Van Wie, Wood, and Otto.

BuildUSD is a software transformation system, so its domain-significant flows are information artifacts and control signals. Electrical or mechanical energy flows are outside the observable responsibilities of this repository and are not invented in the model.

## System function and boundary

The overall function is:

> Transform IFC source and orchestration information into interoperable, georeferenced, semantically traceable USD project artifacts.

Boundary inputs are conversion/federation requests, IFC sources, manifests and options, targeted-enrichment jobs, cancellation state, and an available local or Omniverse runtime. Boundary outputs are layered USD stages, instance caches, semantic graphs, conversion results, targeted-detail replacement manifests, job results, and site/overall federated master stages.

## Primary function chains

### F1 - Convert IFC assets

`SourceSetState` -> interpret conversion intent -> `SelectedSourceSetState` -> discover/load IFC sources -> `ParsedModelSetState` -> resolve model georeference -> `ResolvedModelSetState` -> build geometry prototypes -> `PrototypeCacheSetState` -> author USD layers -> `LayerSetState` -> anchor and geolocate stages -> `AnchoredStageSetState` -> persist semantics/results -> `ConversionResultSetState` and `SemanticGraphSetState`.

The textual model expands layer authoring into prototype, material, instance, and optional 2D geometry actions.

### F2 - Federate USD stages

`AnchoredStageSetState` -> plan stage federation -> `RoutedStageSetState` -> inspect payload anchors -> `InspectedPayloadSetState` -> align payloads -> `AlignedPayloadSetState` -> compose site masters -> `SiteMasterSetState` -> compose/validate overall master -> `FederatedProjectState`.

Projected and geodetic frames are modeled as alternatives inside the alignment and composition functions. Missing-anchor policy, existing-target authority, append-only behavior, rebuild behavior, and idempotence are attributes or control inputs rather than separate structural branches.

### F3 - Run targeted enrichment job

`EnrichmentJob` -> claim job -> `ClaimedJobState` -> resolve detail targets -> `DetailPlanState` -> satisfy targeted detail -> `DetailArtifactSetState` -> publish replacement manifest/archive outcome -> `JobResultState`.

The satisfy function covers either a cache hit or an object-scope detail conversion because both produce the same required output state.

## Function-to-implementation allocation

| Logical element | Primary responsibility | Current implementation |
|---|---|---|
| Command and API adapter | Accept requests and expose results | `api.py`, `cli.py`, `federate_cli.py`, `main.py`, package entry points |
| Conversion orchestrator | Interpret intent, isolate per-file failures, finalize results | `conversion.py` |
| Manifest resolver | Resolve defaults, file rules, master routing, CRS and base points | `config/manifest.py` |
| Source I/O adapter | Discover/read/write local and `omniverse://` artifacts | `io_utils.py`, source collection in `conversion.py` |
| USD runtime adapter | Select Kit or offline bindings and provide `pxr` modules | `usd_context.py`, `kit_runtime.py`, `pxr_utils.py` |
| Georeference planner | Classify authored coordinate space and decide localization | `georef_resolution.py`, `resolve_frame.py`, `geospatial.py` |
| IFC geometry processor | Extract geometry, placement, materials, detail and prototype caches | `process_ifc.py`, `ifc_visuals.py`, `semantic_subcomponents.py`, `occ_detail.py` |
| USD authoring service | Author layers, materials, instances, 2D geometry, anchors and metadata | `process_usd.py` |
| Semantic service | Persist identity/material/decomposition evidence and derive detail targets | `semantic_graph.py`, `semantic_enrichment.py` |
| Federation orchestrator | Plan/rout site and overall masters and maintain target authority | `federation_orchestrator.py` |
| Federation builder | Inspect anchors, align payloads, author composition and validate | `federation_builder.py`, `federation/geodetic_federation.py` |
| Enrichment job service | Convert/cache targeted detail and publish replacement manifests | `jobs.py` |
| Worker queue adapter | Claim, report, and archive file-backed jobs | `worker.py` |

The SysML model contains explicit `allocation` usages from 24 nested functional actions to these logical elements.

## SysML v2 conformance and verification

The model uses SysML 2.0 textual constructs for packages, attribute/item definitions, action definitions/usages, typed input/output parameters, binding connectors, flows, succession flows, port definitions/usages, part definitions/usages, perform actions, and allocations.

It was parsed and validated with the official Systems Modeling Community 2026-04 pilot implementation, Jupyter SysML kernel `0.60.1`, against the bundled normative SysML/KerML libraries. The validation run returned the loaded package with no syntax or semantic validation errors. The pilot-generated SVG is retained as independent evidence that the action model can be consumed by the reference tooling.

The applicable standard is [OMG Systems Modeling Language 2.0](https://www.omg.org/spec/SysML/2.0). The reference implementation and current examples are published in the [SysML v2 Release repository](https://github.com/Systems-Modeling/SysML-v2-Release).

## Scope and assumptions

- The analysis reflects the current dirty worktree, including uncommitted conversion and federation changes present when the model was generated.
- Test modules are verification assets and are not modeled as operational functions.
- Compatibility shims are represented at the command/API boundary, not as separate functional chains.
- Helper-level numerical, mesh, material, and path operations are contained within their parent functions; listing every helper would obscure causal topology.
- The model describes implemented behavior. It does not claim desired behavior beyond evidence in source, tests, and repository documentation.
